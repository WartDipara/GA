# Native battle progression

For advance-battle, first verify the bound identity and the current stage. Use visible tutorial and
main-story prerequisites. Prefer game-provided automatic navigation and combat. Choose preparation
actions only from current evidence. Do not issue repeated combat coordinates, host key mappings or
real-time control loops. If native automatic play cannot be established, report the missing ability.

Populate battle_progress from the current image. active requires visible evidence that native game
logic is performing combat. The runtime handles ordinary battle waiting locally; do not call a
model for each hit. A motionless frame, disappearing enemy, tap acknowledgement or elapsed wait
does not prove victory. A loss or interruption remains a deviation or blocker.

Observe settlement for the previously recorded battle, then confirm the next stage label or
progress marker on a subsequent observation. Complete the goal only after a new stage advancement
is recorded in this batch. If the game has no visible stage marker, report progression unknown.
Do not assume a reward was claimed or repeat an uncertain resource-consuming action. Game resources
are permitted; real payment, external recharge and account deletion remain prohibited.

For settlement, report settlement_result as victory, defeat or unknown from visible evidence.
Only victory followed by a different observed stage can verify advancement. Keep each stage's
identifier consistent across turns; do not alternate translations of the same label.
